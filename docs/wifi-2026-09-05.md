# Nullrunner Wi-Fi stalls — 2026-09-05

## Evidence before the workaround

The user reports repeated silent stalls and severe slowdowns that recover only
after reconnecting Wi-Fi. Other devices usually remain fast, and this laptop's
normal download rate can exceed 500 Mbps. One captured speed test showed
25.40 Mbps down, 139.56 Mbps up, and 300 ms download-loaded latency. Turning off
Proton did not restore normal service.

The affected session used:

- MT7925e, Linux 7.2.3, NetworkManager 1.58.0, wpa_supplicant 2.11.
- Firmware build times `20260605184651a` and `20260605184805`.
- WPA3-SAE with three MLO links at 2462, 5700, and 6615 MHz.
- Excellent signal (about -39 to -42 dBm), reported rates around 1.7–1.9 Gbps,
  and Wi-Fi power saving verified off.
- No active VPN during diagnostic latency tests. Twenty pings to the **local
  router** averaged 60.6 ms, peaking at 187.8 ms. Internet pings averaged 67.4 ms.
  The local result places at least part of the delay before the internet uplink.
- A subsequent bounded 25 MB Cloudflare download averaged 30.1 Mbps. Router
  pings immediately afterward averaged 98.6 ms and peaked at 375.9 ms.

No firmware crash appeared in the event's kernel log. That does not exclude a
silent driver queue stall. The kernel queue pointers were not captured here, so
the precise upstream failure signature has not been proven on this laptop.

The [upstream regression report](https://lists.infradead.org/pipermail/linux-mediatek/2026-August/112117.html)
bisected a silent MT7925 MLO stall to `ff643b81bc38`, introduced between Linux 7.0
and 7.1, with exactly the same firmware build. A
[second reproduction](https://lists.infradead.org/pipermail/linux-mediatek/2026-August/112358.html)
on another machine/access point found that the 5 + 6 GHz pair stalls even with
newer August firmware. This is a strong candidate, not a complete diagnosis of
every Wi-Fi, suspend, or VPN symptom.

## Workaround

`hosts/nullrunner/wifi.nix` overrides only nullrunner's wpa_supplicant package.
It removes the assignment that advertises the nl80211 MLO capability to the
supplicant. The MT7925 uses the supplicant's SME authentication path, whose MLO
negotiation is guarded by that capability. It should therefore associate using
one link. WPA3 and ordinary band/channel selection are retained. The kernel,
firmware, saved credentials, IPv6, and VPN kill-switch policy are unchanged.

This is a **local capability workaround**, not an upstream patch or a guaranteed
throughput improvement. Its cost is foregoing multi-link operation until the
driver regression is fixed. The override uses `--replace-fail` so a source update
cannot silently omit it. `iw` is installed for inspecting the real radio state.

A temporary copy of the saved WPA3 profile restricted to 5 GHz still established
**two MLO links, at 5700 and 6615 MHz**. It also dropped two of twelve immediate
router pings. That test profile was deleted and the original profile restored.
Do not mistake a NetworkManager band restriction for an MLO disable switch.

## Apply and verify

The user applies the system configuration with `nrs`. It changes the supplicant
service executable and can briefly interrupt Wi-Fi. No kernel change or reboot is
required by this workaround. Agents should build and evaluate first:

```bash
nix flake check
nix build --no-link .#nixosConfigurations.nullrunner.pkgs.wpa_supplicant
```

After activation:

```bash
systemctl show wpa_supplicant.service -p MainPID -p ActiveState
readlink -f /run/current-system/sw/bin/wpa_supplicant
journalctl -b -u wpa_supplicant --since '5 minutes ago'
iw dev wlp191s0 link
iw dev wlp191s0 station dump
nmcli -f NAME,TYPE,DEVICE connection show --active
```

The journal should include `MLO disabled by nullrunner MT7925 workaround`, and
`iw` should show one ordinary connection/frequency rather than multiple `Link N`
entries and `MLD` statistics. Check the running process executable as well as the
installed symlink if activation leaves any doubt about which binary is running.

Compare router latency and download speed without the VPN, then with the VPN.
Repeat after ordinary use and sleep/resume. A brief good sample immediately after
reconnecting cannot establish that the recurring stall is fixed. Do not add a
timer that continually resets Wi-Fi; it would interrupt traffic and hide evidence.

To remove the workaround after an upstream fix is verified, remove only the
`nixpkgs.overlays` block in `hosts/nullrunner/wifi.nix`, validate, and apply with
`nrs`. Keep the NetworkManager settings and diagnostic package. This restores the
stock supplicant without editing saved profiles.

## VPN disconnect delay

At 16:37:56 local time, Proton logged the disconnect click and NetworkManager
removed the tunnel promptly. Proton stayed in its disconnecting state until
16:38:31, when its local-agent connection timed out and it removed the kill-switch
connection. That explains about 35 seconds of the observed delay in this event;
it does not account for the user's entire estimated two minutes. The subsequent
Wi-Fi failure persisted without the VPN. No kill-switch bypass was introduced.

## Verification status

- `nix fmt -- --check` and `nix flake check` passed for both hosts. The unchanged
  script check was already cached. Existing upstream deprecation warnings remain.
- The modified wpa_supplicant compiled successfully with four build jobs. Its
  version command runs and its binary contains the workaround journal message.
- The complete nullrunner system closure built successfully. The generated
  service PATH and installed executable both select the modified supplicant.
  The kernel is exactly the same store path as the running system's kernel.
- The single-link workaround has **not yet been activated or validated on the
  radio**. Packet latency, throughput, and longer-term stability remain to test.
